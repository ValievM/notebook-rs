# Архитектура

Принцип: **границы через трейты** (порты), конкретные реализации (адаптеры) за ними, склейка в одном месте. В Rust нет наследования, поэтому ООП-паттерны здесь строятся на трейтах и композиции, а не на классах. Не всё из SOLID нужно: подход «сначала маленький трейт, потом реализация» даёт то же самое (подмена, тесты с фейками) без лишних слоёв.

```
main.rs (CLI)  ──►  service::Notebooks (фасад)
                       │
   ┌───────────────────┼───────────────────────────┐
   ▼                   ▼                           ▼
chunk::Chunker     embed::Embedder          retrieve::Retriever ──► answer (промпт + проверка цитат)
(стратегия)        (порт+адаптеры)          Bm25 / Vector / Hybrid        │
                                                  │                       ▼
                                                  ▼                  llm::Llm
                                             store::Store            (порт+адаптеры)
                                             (репозиторий, SQLite)
```

## Модули
| Модуль | Роль |
|---|---|
| `domain` | Слова предметной области: `NotebookId`, `PassageId` (newtype), `Passage`. |
| `error` | Единый `Error` (thiserror). `anyhow` только в `main.rs`. |
| `chunk` | Трейт `Chunker`, `ParagraphChunker`. Режет источник на фрагменты. |
| `chunk_markdown` | `MarkdownChunker`: по заголовкам, путь заголовков в тексте фрагмента, перекрытие по предложениям. Стандартная нарезка. |
| `metrics` | Мониторинг: `Recorder` (порт), `Clock` (подменяемые часы), `Metrics` + `Span` (замер участка), `SqliteRecorder` (запись в `metrics.db` через канал и поток-писатель), `summarize` (сводка с процентилями), `report` (текст для `nb stats`), декораторы `InstrumentedLlm/Embedder/Retriever`. См. раздел «Метрики». |
| `view` | `source_view`: источник для чтения с отмеченной цитатой (`before` / `hit` / `after`). Место цитаты находит `answer::locate` по той же нормализации, по которой цитата проверяется. |
| `source` | Трейт `Reader` (читает один вид источника), цепочка `Sources`; `WebReader`, `PdfReader`, `TextReader`. Выход читателя это недоверенный текст. |
| `embed` | Трейт `Embedder` (`embed` для фрагментов, `embed_query` для вопроса), `HashingEmbedder` (офлайн), `cosine`. Вектор помечен именем модели. |
| `embed_fast` | `FastEmbedder` (fastembed, E5-small multilingual, 8-битная квантованная версия, 113 МБ): файлы скачиваются один раз (`Fetch`, запись через `.part`), каждый текст считается отдельно. Только с `--features fastembed`. |
| `store` | Репозиторий над SQLite: FTS5 (BM25) и векторы (BLOB). Единственное место с SQL, миграции через `user_version`. |
| `retrieve` | Трейт `Retriever`; `Bm25Retriever`, `VectorRetriever`, `HybridRetriever` + `reciprocal_rank_fusion`. |
| `parallel` | `map_ordered`: fork-join на `thread::scope`; `testing::Rendezvous` для тестов. См. раздел «Параллелизм». |
| `deep` | Режим `--deep`: план поисков от модели (`parse_plan`), поиски, слияние RRF, один ответ. Принимает `&dyn Llm` и `&dyn Retriever`, поэтому тестируется на фейках. |
| `digest` | Надстройки над целыми источниками: `summarize` (конспект) и `compare` (сравнение двух источников). Помещается в бюджет: один вызов; длиннее: части параллельно, затем сводка по проверенным цитатам. |
| `answer` | Промпт с пронумерованными фрагментами, разбор JSON, проверка цитат подстрокой. |
| `llm` | Трейт `Llm`; адаптер `CodexExec`. |
| `service` | Фасад `Notebooks`: `add_source`, `ask`, `ask_deep`, `summarize`, `compare`; `standard()` собирает обычную связку. |

## Паттерны (и где они)
- **Порт и адаптер (hexagonal)**: `Llm`, `Embedder`, `Store` (репозиторий). Ядро не знает, что за ним `codex` или SQLite.
- **Стратегия**: `Chunker`; позже Markdown/по токенам рядом с абзацным.
- **Компоновщик (composite)**: `HybridRetriever` сам `Retriever` и состоит из `Retriever`-ов.
- **Цепочка обязанностей**: `Sources` (читатели по очереди, первый подходящий читает).
- **Фасад**: `Notebooks`.
- **Newtype**: идентификаторы нельзя перепутать.
- **Репозиторий**: `Store` прячет SQL; потокобезопасен (`Mutex<Connection>`) для будущего окна.
- Запланировано: **декоратор** (`RetryingLlm`, `CachingEmbedder` вокруг любой реализации), **строитель** для `Notebooks`, когда появится больше настроек.

## Правила
- Новая возможность = новый трейт или новая реализация существующего, а не `if` в чужом коде.
- Тесты используют фейки через трейты (`Recording`, `Fixed`); сети и настоящей модели в тестах нет.
- Вектор сравнивается только с векторами той же модели (`embedding_model` в таблице): смена модели не ломает поиск, старые вектора просто не используются, пока источник не загружен заново.

## Окно (Tauri)

```
ui/ (HTML, CSS, JS без сборщика)  --invoke-->  src-tauri/src/lib.rs (команды)  -->  notebook_rs::service::Notebooks
        ^                                              |                                  (то же ядро, что у `nb`)
        '------------- DTO (camelCase JSON) <---------'
```

| Часть | Роль |
|---|---|
| `src-tauri/src/lib.rs` | Тонкие команды: берут движок, выполняют работу в `spawn_blocking` (вызов модели занимает секунды и не должен замораживать окно), возвращают простые данные. Логики блокнота здесь нет. |
| `Engine` (`OnceLock`) | Базу и модель эмбеддингов создаёт фоновый поток: окно открывается сразу, а при первом запуске (скачивание модели) показывает баннер. `OnceLock`: записывается один раз, читается многими без блокировок. Команды до готовности отвечают «поиск готовится». |
| `src-tauri/src/dto.rs` | Формы данных для страницы (camelCase) и русские тексты ошибок (`user_message`). |
| `ui/app.js` | Весь интерфейс. Текст источников и ответов модели недоверенный: попадает в страницу только текстовыми узлами (`h()` не умеет HTML), `innerHTML` не используется. |
| `ui/dev/mock.js` | Заглушка движка для просмотра вёрстки в обычном браузере (`python3 -m http.server` в `ui/`); в приложении не загружается. |

Безопасность окна: CSP `default-src 'self'` без `unsafe-inline`; в `capabilities/default.json` только `core:default` и диалог выбора файлов; Tauri сам не пускает к своим командам страницы с чужого адреса (тесты используют `tauri://localhost`, как настоящее окно).

Общая папка: окно и `nb` используют `~/.notebook-rs/` (база и модели). Ограничение: это два процесса, кэш векторов в окне не знает о записях, сделанных из `nb` во время работы окна (полнотекстовый поиск увидит их сразу, векторный после перезапуска окна).

Тесты окна идут через настоящую IPC Tauri без окна (`tauri::test`): имена аргументов (`notebookId`), `null` в необязательных аргументах, формат ответов, русские ошибки.

## Метрики

Что измеряется (всё через `Metrics::span(kind)`; ничего не пишется, если метрики выключены):

| Вид (`kind`) | Где | Что внутри |
|---|---|---|
| `ask`, `ask_deep`, `summarize`, `compare` | `Notebooks` | вся операция; `subject` = источник или `*`; `question_chars` |
| `source.add` и внутри него `source.chunk`, `store.write`, `embed.passages` | `Notebooks`, декоратор | название источника, `chars`, `passages` |
| `source.read` | `Sources::with_metrics` | адрес или путь, `chars`; **здесь ловятся «особые файлы»** |
| `llm.complete` | `InstrumentedLlm` | `prompt_chars`, `reply_chars` |
| `embed.query`, `embed.passages` | `InstrumentedEmbedder` | `chars`, `texts` |
| `retrieve.bm25`, `retrieve.vector`, `retrieve.hybrid` | `InstrumentedRetriever` | `limit`, `results` |
| `engine.start`, `engine.model_load` | окно / `nb` | время запуска и загрузки модели |
| `memory.after_start`, `memory.after_add`, `memory.after_model_load` | `Metrics::sample_memory` | `rss_bytes` процесса (через `ps`) |
| `memory.periodic` | `MemorySampler` (окно) | то же раз в 30 с, пока окно открыто: показывает тренд (растёт ли память, пока окно стоит). Поток ждёт на канале с таймаутом, поэтому остановка мгновенная; при остановке дожидается замера, который уже идёт |
| `command.*` | команды окна | время, которое ждал человек; включает ожидание блокировки эмбеддера |

Паттерны: **декоратор** (`Instrumented*` делают то же, что обёрнутое, и мерят), **порт** (`Recorder`), **внедрение часов** (`Clock`: `ManualClock` в тестах даёт точные длительности без `sleep`), **span** (замер участка: пишет и успех, и ошибку).

Синхронизация: запись идёт через **канал** (`mpsc`) в один поток-писатель, владеющий соединением SQLite; события из многих потоков складываются в очередь, писатель пишет пачками в одной транзакции. Здесь канал нужен (много производителей, один потребитель, никто не ждёт ответа), в отличие от поиска. `Sender` потокобезопасен; `flush()` ждёт ответа через `sync_channel(1)`; `Drop` закрывает канал и дожидается писателя, поэтому ничего не теряется при выходе. Если диск сломан, события теряются, программа работает дальше. Файл в режиме WAL: `nb stats` читает его, пока окно пишет.

Что хранится: время, длительность, успех, числа (размеры, количества, байты), **название источника** (адрес, путь, заголовок) и **сообщение ошибки** (до 300 символов). Не хранится: текст источников, вопросы, ответы. Файл `~/.notebook-rs/metrics.db`, хранение 30 дней (старое удаляется при открытии). Отключить в `nb`: `--no-metrics`.

## Параллелизм и синхронизация

Сначала что реально медленно: вызов Codex это секунды, поиск и разбор это миллисекунды. Поэтому параллелить поиск ради скорости ответа почти бесполезно; полезно (а) не делать лишнюю работу на каждый вопрос (кэш) и (б) не складывать время независимых частей.

| Где | Примитив | Зачем и почему именно он |
|---|---|---|
| `parallel::map_ordered` | `std::thread::scope` (fork-join) | Независимые задачи (части гибридного поиска, поиски плана `--deep`) идут одновременно, результаты возвращаются в порядке задач, паника в задаче перебрасывается вызывающему. Потоки «scoped»: могут брать данные взаймы без `Arc` и гарантированно завершаются до выхода из функции. Поток на задачу допустим, пока список короткий по построению (части поиска, ≤5 поисков). Это не пул: список из пользовательских данных ему не давать. |
| `Store.db` | `Mutex<Connection>` | Соединение SQLite обслуживает один запрос за раз; писатель не должен перемешиваться с читателем. Мьютекс, а не `RwLock`: читать из одного соединения параллельно всё равно нельзя. |
| `Store.vectors` | `RwLock<VectorCache>` + `Arc` | Кэш читает каждый вопрос, сбрасывает только запись: много читателей сразу, редкий писатель. Значения в `Arc`, поэтому читатель получает ссылку, а не копию тысяч векторов. |
| `VectorCache.generation` | счётчик под тем же `RwLock` | Защита от гонки «загрузил до записи, положил после сброса»: кэш принимает загруженное только если поколение не изменилось. Проверено детерминированным тестом через шов `embedded_passages_with`. |
| `CodexExec` (папка вызова) | `AtomicU64` + `Ordering::Relaxed` | Каждый вызов `codex exec` получает свою временную папку (`pid-счётчик`): вызовы идут параллельно, общий файл ответа перемешал бы их. Важна только уникальность значения, а не порядок между потоками, поэтому достаточно `Relaxed`. Проверено тестом с поддельным `codex`, который «думает» 0,3 с. |
| `FastEmbedder.model` | `Mutex<TextEmbedding>` | `embed` берёт `&mut self`; нужен эксклюзивный доступ. Внутри ONNX Runtime сам использует все ядра, так что параллельные вызовы снаружи ничего бы не ускорили. |

Правила:
- Никакой метод не держит одну блокировку, пока берёт другую. Порядок «кэш → файл → кэш» держит каждую по отдельности, поэтому взаимной блокировки (deadlock) нет.
- Блокировка не держится на время вызова внешнего компонента (модель, эмбеддер).
- Не нужны и не используются: каналы в поиске (нет потока сообщений между потоками; в мониторинге они есть, см. «Метрики»), атомики в продакшн-коде (счётчик поколения лежит под `RwLock`, отдельный атомик только усложнил бы доказательство), `async`/tokio (нагрузка это процессор плюс блокирующий подпроцесс `codex`). Пересмотреть при появлении окна (Tauri) или сервера: там нужен неблокирующий ввод-вывод.
- Тесты на параллельность не спят и не меряют время: `Rendezvous` (в `parallel::testing`) пропускает задачу только если все задачи внутри одновременно; при последовательном запуске первая получает таймаут и тест падает.

Известные пределы: чтение из SQLite идёт через один `Mutex`; при большом числе одновременных читателей понадобится пул соединений в режиме WAL (пока не измерено, не делаем). Поиски `--deep` эмбеддят вопросы по одному под мьютексом эмбеддера; пакетный вызов `embed` на все поиски сразу был бы быстрее (в планах).

## Границы масштаба
Поиск векторов перебором по одному блокноту: мгновенно до десятков тысяч фрагментов. Если упрёмся, ADR в `DECISIONS.md` (D-04) называет следующий шаг.
