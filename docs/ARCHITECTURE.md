# Архитектура

Принцип: **границы через трейты** (порты), конкретные реализации (адаптеры) за ними, склейка в одном месте. В Rust нет наследования, поэтому ООП-паттерны здесь строятся на трейтах и композиции, а не на классах. Не всё из SOLID нужно: подход «сначала маленький трейт, потом реализация» даёт то же самое (подмена, тесты с фейками) без лишних слоёв.

```
main.rs (CLI)  ──►  service::Notebooks (фасад)
                       │
   ┌───────────────────┼───────────────────────────┐
   ▼                   ▼                           ▼
chunk::Chunker     embed::Embedder          retrieve::Retriever ──► answer (промпт + проверка цитат)
(стратегия)        (порт+адаптеры)          Bm25 / Vector / Hybrid        │
                                                  │                       ▼
                                                  ▼                  llm::Llm
                                             store::Store            (порт+адаптеры)
                                             (репозиторий, SQLite)
```

## Модули
| Модуль | Роль |
|---|---|
| `domain` | Слова предметной области: `NotebookId`, `PassageId` (newtype), `Passage`. |
| `error` | Единый `Error` (thiserror). `anyhow` только в `main.rs`. |
| `chunk` | Трейт `Chunker`, `ParagraphChunker`. Режет источник на фрагменты. |
| `chunk_markdown` | `MarkdownChunker`: по заголовкам, путь заголовков в тексте фрагмента, перекрытие по предложениям. Стандартная нарезка. |
| `source` | Трейт `Reader` (читает один вид источника), цепочка `Sources`; `WebReader`, `PdfReader`, `TextReader`. Выход читателя это недоверенный текст. |
| `embed` | Трейт `Embedder` (`embed` для фрагментов, `embed_query` для вопроса), `HashingEmbedder` (офлайн), `cosine`. Вектор помечен именем модели. |
| `embed_fast` | `FastEmbedder` (fastembed, E5), только с `--features fastembed`. |
| `store` | Репозиторий над SQLite: FTS5 (BM25) и векторы (BLOB). Единственное место с SQL, миграции через `user_version`. |
| `retrieve` | Трейт `Retriever`; `Bm25Retriever`, `VectorRetriever`, `HybridRetriever` + `reciprocal_rank_fusion`. |
| `parallel` | `map_ordered`: fork-join на `thread::scope`; `testing::Rendezvous` для тестов. См. раздел «Параллелизм». |
| `deep` | Режим `--deep`: план поисков от модели (`parse_plan`), поиски, слияние RRF, один ответ. Принимает `&dyn Llm` и `&dyn Retriever`, поэтому тестируется на фейках. |
| `answer` | Промпт с пронумерованными фрагментами, разбор JSON, проверка цитат подстрокой. |
| `llm` | Трейт `Llm`; адаптер `CodexExec`. |
| `service` | Фасад `Notebooks`: `add_source`, `ask`, `ask_deep`; `standard()` собирает обычную связку. |

## Паттерны (и где они)
- **Порт и адаптер (hexagonal)**: `Llm`, `Embedder`, `Store` (репозиторий). Ядро не знает, что за ним `codex` или SQLite.
- **Стратегия**: `Chunker`; позже Markdown/по токенам рядом с абзацным.
- **Компоновщик (composite)**: `HybridRetriever` сам `Retriever` и состоит из `Retriever`-ов.
- **Цепочка обязанностей**: `Sources` (читатели по очереди, первый подходящий читает).
- **Фасад**: `Notebooks`.
- **Newtype**: идентификаторы нельзя перепутать.
- **Репозиторий**: `Store` прячет SQL; потокобезопасен (`Mutex<Connection>`) для будущего окна.
- Запланировано: **декоратор** (`RetryingLlm`, `CachingEmbedder` вокруг любой реализации), **строитель** для `Notebooks`, когда появится больше настроек.

## Правила
- Новая возможность = новый трейт или новая реализация существующего, а не `if` в чужом коде.
- Тесты используют фейки через трейты (`Recording`, `Fixed`); сети и настоящей модели в тестах нет.
- Вектор сравнивается только с векторами той же модели (`embedding_model` в таблице): смена модели не ломает поиск, старые вектора просто не используются, пока источник не загружен заново.

## Параллелизм и синхронизация

Сначала что реально медленно: вызов Codex это секунды, поиск и разбор это миллисекунды. Поэтому параллелить поиск ради скорости ответа почти бесполезно; полезно (а) не делать лишнюю работу на каждый вопрос (кэш) и (б) не складывать время независимых частей.

| Где | Примитив | Зачем и почему именно он |
|---|---|---|
| `parallel::map_ordered` | `std::thread::scope` (fork-join) | Независимые задачи (части гибридного поиска, поиски плана `--deep`) идут одновременно, результаты возвращаются в порядке задач, паника в задаче перебрасывается вызывающему. Потоки «scoped»: могут брать данные взаймы без `Arc` и гарантированно завершаются до выхода из функции. Поток на задачу допустим, пока список короткий по построению (части поиска, ≤5 поисков). Это не пул: список из пользовательских данных ему не давать. |
| `Store.db` | `Mutex<Connection>` | Соединение SQLite обслуживает один запрос за раз; писатель не должен перемешиваться с читателем. Мьютекс, а не `RwLock`: читать из одного соединения параллельно всё равно нельзя. |
| `Store.vectors` | `RwLock<VectorCache>` + `Arc` | Кэш читает каждый вопрос, сбрасывает только запись: много читателей сразу, редкий писатель. Значения в `Arc`, поэтому читатель получает ссылку, а не копию тысяч векторов. |
| `VectorCache.generation` | счётчик под тем же `RwLock` | Защита от гонки «загрузил до записи, положил после сброса»: кэш принимает загруженное только если поколение не изменилось. Проверено детерминированным тестом через шов `embedded_passages_with`. |
| `FastEmbedder.model` | `Mutex<TextEmbedding>` | `embed` берёт `&mut self`; нужен эксклюзивный доступ. Внутри ONNX Runtime сам использует все ядра, так что параллельные вызовы снаружи ничего бы не ускорили. |

Правила:
- Никакой метод не держит одну блокировку, пока берёт другую. Порядок «кэш → файл → кэш» держит каждую по отдельности, поэтому взаимной блокировки (deadlock) нет.
- Блокировка не держится на время вызова внешнего компонента (модель, эмбеддер).
- Не нужны и не используются: каналы (нет потока сообщений между потоками), атомики в продакшн-коде (счётчик поколения лежит под `RwLock`, отдельный атомик только усложнил бы доказательство), `async`/tokio (нагрузка это процессор плюс блокирующий подпроцесс `codex`). Пересмотреть при появлении окна (Tauri) или сервера: там нужен неблокирующий ввод-вывод.
- Тесты на параллельность не спят и не меряют время: `Rendezvous` (в `parallel::testing`) пропускает задачу только если все задачи внутри одновременно; при последовательном запуске первая получает таймаут и тест падает.

Известные пределы: чтение из SQLite идёт через один `Mutex`; при большом числе одновременных читателей понадобится пул соединений в режиме WAL (пока не измерено, не делаем). Поиски `--deep` эмбеддят вопросы по одному под мьютексом эмбеддера; пакетный вызов `embed` на все поиски сразу был бы быстрее (в планах).

## Границы масштаба
Поиск векторов перебором по одному блокноту: мгновенно до десятков тысяч фрагментов. Если упрёмся, ADR в `DECISIONS.md` (D-04) называет следующий шаг.
