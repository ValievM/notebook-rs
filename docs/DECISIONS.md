# Решения

Формат: что выбрали, что сравнивали, почему, когда пересмотреть. Только подтверждённое помечено фактом; остальное: допущение/решение Claude.

## D-01. Язык: Rust (решение владельца: «хочется на расте»)
Готового NotebookLM-подобного проекта на Rust поиск не нашёл. Ближайшие: Open Notebook (Python + Next.js + SurfaceDB, Docker), KnowNote (Electron, GPL-3.0), Notex (Go). Делаем своё.

## D-02. Образец функций: Open Notebook (MIT)
Прочитан код: нарезка 400 токенов/15% перекрытия, поиск полнотекстовый и векторный **раздельно** (без объединения), агрегирование по источнику, цитата = `[source:id]` **без проверки**. Что берём: схему «стратегия → поиски → частичные ответы → синтез» (в планах). Что делаем иначе: проверка цитат, гибрид через RRF, поиск по фрагментам, а не по источникам.

## D-03. Другие проекты, на которые стоит смотреть (по описаниям, код не читал)
- **Kotaemon**: гибридный поиск, реранкер, цитаты с подсветкой в PDF. Образец для интерфейса «переход к месту в источнике». Активность в 2026 снизилась.
- **SurfSense** (Apache-2.0): двухуровневый RAG, гибридный поиск, реранкеры. Образец для реранкера.
- **AnythingLLM**: поиск проще, но режим «не отвечать, если ничего не нашлось» полезен (у нас уже есть).
Проверка цитат подстрокой ни в одном из описаний не найдена. Дата проверки: 2026-10-25; перед заимствованием идей читать их код, не пересказы.

## D-04. Хранилище: SQLite (FTS5 + векторы BLOB), без отдельной векторной БД
Сравнивали: LanceDB (встраиваемый, есть RRF и реранкеры, но документация для Rust тонкая), sqlite-vec, tantivy (по ним данных не нашёл, не сравнивал). Выбор: одна SQLite, перебор косинуса внутри блокнота. Причина: ноль новых зависимостей, один файл, личный масштаб. Пересмотреть: поиск медленнее ~100 мс на блокнот (порядка сотен тысяч фрагментов); тогда LanceDB для векторов, BM25 остаётся в FTS5, объединение RRF уже наше.

## D-05. Эмбеддинги: трейт `Embedder`; сейчас `HashingEmbedder`, дальше fastembed-rs
fastembed-rs (ONNX Runtime + токенизаторы Hugging Face) по описаниям самый простой путь для локальных эмбеддингов и реранкера; candle нужен, только если модели нет в ONNX. Скачивание модели (сотни МБ) и ONNX Runtime: **согласовать до подключения**, подключать за cargo-фичей, чтобы базовая сборка осталась лёгкой. `HashingEmbedder` ловит слова в разных формах, но не синонимы; это временная заглушка, а не «семантика».

## D-06. Фреймворки LLM (rig, swiftide): не берём
Rig: единый API к провайдерам; Swiftide: потоки индексации для RAG. Наш `Llm` это один метод, а `codex exec` и вход через ChatGPT они не поддерживают. Фреймворк добавил бы вес без выгоды. Пересмотреть, если понадобятся агенты с инструментами.

## D-07. Модель: Codex по подписке
Сейчас `codex exec` (вход владельца через `codex login`, токены программа не видит и не копирует; владелец предложил использовать его токен из локального файла: **отказались**, это чужой токен в стороннем приложении). Официальный путь «Sign in with ChatGPT» (OAuth, client ID, `/v1/responses`, `codex app-server`) существует; условия регистрации client ID для личного проекта **не проверены**. Пока не проверено, `codex exec` остаётся временным адаптером, а `Llm` позволяет заменить его без правок ядра.

## D-08. Цитаты: дословная подстрока в названном фрагменте
Нормализация: пробелы схлопываются, регистр не важен. Отброшенные цитаты считаются и показываются. Ограничение: перефразированная модель-цитата будет отброшена (это сознательно: лучше потерять цитату, чем показать неверную).
