## D-04. Хранилище: SQLite (FTS5 + векторы BLOB), без отдельной векторной БД
Сравнивали: LanceDB (встраиваемый, есть RRF и реранкеры, но документация для Rust тонкая), sqlite-vec, tantivy (по ним данных не нашёл, не сравнивал). Выбор: одна SQLite, перебор косинуса внутри блокнота. Причина: ноль новых зависимостей, один файл, личный масштаб. Пересмотреть: поиск медленнее ~100 мс на блокнот (порядка сотен тысяч фрагментов); тогда LanceDB для векторов, BM25 остаётся в FTS5, объединение RRF уже наше.

## D-06. Фреймворки LLM (rig, swiftide): не берём

## D-08. Цитаты: дословная подстрока в названном фрагменте
Нормализация: пробелы схлопываются, регистр не важен. Отброшенные цитаты считаются и показываются. Ограничение: перефразированная модель-цитата будет отброшена (это сознательно: лучше потерять цитату, чем показать неверную).

## D-10. Параллелизм: scoped-потоки и кэш векторов, без async и без пула (решение Claude, 2026-10-25, по запросу владельца «параллелить, что можно»)
Выбор по измерению узких мест, а не «параллелим всё»: ответ занимает секунды из-за модели, поиск миллисекунды. Сделано: (1) независимые поиски идут одновременно на `std::thread::scope`; (2) кэш векторов блокнота под `RwLock`, что убирает чтение и декодирование всех векторов на каждый вопрос. Сравнивали: rayon (лишняя зависимость для списков из 2-5 элементов; пересмотреть для перебора косинуса по сотням тысяч векторов), tokio/async (нагрузка не ввод-вывод в сокетах; пересмотреть для окна или сервера), пул соединений SQLite (не измерено). Подробности примитивов: ARCHITECTURE.

## D-09. Глубокий вопрос: план поисков, слияние, один ответ (решение Claude, 2026-10-25)
Open Notebook: стратегия → по каждому поиску частичный ответ → итоговый ответ (N+2 вызова модели, цитаты привязаны к источникам и не проверяются). Здесь: план (1 вызов) → поиски → слияние RRF в один пронумерованный пул до 12 фрагментов → ответ (1 вызов), цитаты проверяются как обычно. Причины: бюджет это подписка, лишние вызовы дороги; частичные ответы ломают сквозную нумерацию цитат; 12 фрагментов по ~1000 символов без труда помещаются в один промпт. Пересмотреть, если блокноты станут такими, что нужны сотни фрагментов на вопрос (тогда частичные ответы как сжатие контекста, с проверкой цитат на каждом шаге).

## D-11. Источники: PDF и веб (решение Claude, 2026-10-25)
- **PDF: `pdf-extract`** (чистый Rust). Сравнивали по описаниям: `lopdf` (нет извлечения текста), `pdf_oxide` (заявляет лучший результат, цифры самих авторов, не проверены), `pdfium-render`/`mupdf` (нужны внешние библиотеки). Проверка на настоящем русском PDF (встроенный шрифт, сделан через CoreText) прошла: текст без искажений. Запасной вариант при проблемах с другими PDF: `pdf_oxide` за тем же трейтом `Reader`. Известные границы: сканы (картинки текста) отклоняются с подсказкой про OCR; сложная вёрстка (колонки, таблицы) может перемешаться. Разбор PDF обёрнут в `catch_unwind`, потому что `pdf-extract` на битых файлах бывает паникует; сам этот случай тестом не воспроизведён.
- **Веб: `ureq` + `dom_smoothie` + `htmd`.** `ureq` блокирующий и маленький (нагрузка не сетевая, async не нужен); `dom_smoothie` порт Mozilla Readability (оставляет статью без меню и подвала); `htmd` HTML в Markdown с заголовками. Не страница-статья: конвертируется целиком, а не отклоняется. Ограничения безопасности: только http/https, без cookie и учётных данных, таймаут 30 с, лимит ответа 10 МБ. Прокси берутся из окружения (поведение `ureq` по умолчанию).
- **Недоверенный текст.** Веб-страницы и PDF могут содержать инструкции для модели. Защита: промпт требует отвечать только по фрагментам, а каждая цитата проверяется по тексту (D-08). Полной защиты от prompt injection это не даёт: ответ модели всё равно может быть искажён текстом источника, поэтому в UI цитаты нужно показывать рядом с ответом.
- Адрес `localhost` и частные адреса не блокируются (нужны тестам и локальным документам); если программа станет сервисом для других людей, добавить запрет (SSRF).

## D-12. Надстройки: конспект и сравнение поверх одного механизма (решение Claude, 2026-10-25)
- **Один механизм, два задания.** `summarize` и `compare` это «задание + пронумерованные фрагменты + проверка цитат» (`answer::ask_task`). Новая надстройка (план, карточки) добавляется заданием, а не новым кодом проверки.
- **Бюджет, а не лимит модели.** Один вызов получает до 40 000 символов (около 13 тысяч токенов русского): дольше и дороже без выгоды для качества конспекта. Длиннее: части по порядку чтения, до 6 штук, параллельно, затем сводка. Больше 6 частей: отказ до всяких вызовов с подсказкой (задать вопрос или добавлять источники по одному), потому что тихая обрезка исказила бы конспект.
- **Сводка видит только процитированное.** Сводящий вызов получает тексты частичных конспектов и те фрагменты, на которые они ссылаются (цитаты в них уже проверены), а не весь материал заново. Номера фрагментов сквозные, поэтому ссылка из любой части означает один и тот же фрагмент. Отброшенные цитаты частей суммируются в итоговом счёте.
- **Сравнение длинных источников:** конспект каждого по очереди (внутри конспекта части параллельно; два источника одновременно дали бы до 12 процессов `codex` на одну подписку), затем сравнение по конспектам и процитированным фрагментам.
- **Ограничение (известно):** модель может цитировать абзац целиком (в живой проверке так и было), цитата при этом проверена, но длинная. Если мешает, ужесточить задание.

## D-13. Окно: Tauri 2 с интерфейсом на чистом HTML/JS (решение Claude, 2026-10-25)
- **Tauri, а не Electron:** ядро на Rust подключается напрямую (без процесса-посредника), нет Chromium в поставке, маленькое приложение. Tauri 2.12.
- **Без Node и сборщика.** Интерфейс это три файла (`ui/index.html`, `style.css`, `app.js`): `cargo run -p notebook-rs-app` достаточно, `npm` не нужен. Платой за это стало отсутствие фреймворка; пока экранов мало, это дешевле. Пересмотреть, если интерфейс вырастет до нескольких сложных экранов.
- **Диалог выбора файлов** через официальный плагин `tauri-plugin-dialog`, перетаскивание файлов через событие окна Tauri.
- **Движок в фоне:** первый запуск скачивает модель, окно не должно висеть без объяснений.
- **Цитата открывает источник на нужном месте:** `answer::locate` возвращает диапазон в исходном тексте по той же нормализации, что и проверка цитат (одна реализация на оба случая, поэтому «принято как цитата» и «найдено в тексте» не могут разойтись).
- **Не проверено (честно):** сборка установочного пакета `.app`/`.dmg` (`cargo tauri build` не запускался, нужен `cargo install tauri-cli` и иконка в формате `.icns`); внешний вид самого окна macOS: вёрстка проверена в браузере на заглушке (светлая и тёмная темы), запуск настоящего окна проверен только по тому, что процесс живёт и движок готов.

## D-14. Память: квантованная модель вместо полной (решение Claude, 2026-10-25, после жалобы «Системе не хватает памяти»)
**Что случилось.** Окно заняло 3,7 ГБ, а на машине (16 ГБ) уже работали Docker, редактор, браузер и Claude. Это не моё предположение, а замеры (`/usr/bin/time -l`, пиковая резидентная память):

| Вариант | Пик |
|---|---|
| Полная модель (448 МБ), загрузка | 3,82 ГБ (потом 1,4-1,9 ГБ) |
| то же, текст в 1 МБ (420 фрагментов), пачка 256 | 5,1 ГБ, 104 с |
| то же, пачка 16 | 9,75 ГБ, 100 с (хуже) |
| Настройки ONNX Runtime (арена, предупаковка, 1/4 потоков, KleidiAI), релизная сборка | без изменений: 3,8 ГБ |
| **Квантованная модель (113 МБ), загрузка** | **0,93 ГБ** |
| то же, окно целиком | 1,0 ГБ стабильно |
| то же, текст в 1 МБ | 1,8 ГБ, 58 с |

**Чего не оказалось верным.** Первая гипотеза «виновата большая пачка» была неверной: пачки поменьше не помогли. Настройки ONNX Runtime и релизная сборка тоже ничего не дали. Помогла только модель поменьше.

**Что сделано.** Файлы квантованной E5-small (`Xenova/multilingual-e5-small`, int8) скачиваются один раз в `~/.notebook-rs/models/e5-small-q8/`. Модель названа иначе (`fastembed-multilingual-e5-small-q8`): векторы старой модели не смешиваются с новыми, источники нужно добавить заново. Динамически квантованная модель масштабирует числа по пачке, поэтому вектор текста зависел бы от соседей: **каждый текст считается отдельно** (тест: вектор один и тот же в одиночку и в компании). Смысл проверен тестом и живым вопросом синонимами.

**Известные пределы.** Старая полная модель остаётся на диске (465 МБ): `rm -r ~/.notebook-rs/models/models--intfloat--multilingual-e5-small`. Квантование чуть снижает точность векторов; на проверенных примерах поиск находил те же фрагменты. Если окно всё равно мешает другим программам: загружать модель только при первом вопросе или добавлении и выгружать после простоя (не сделано).

## D-15. Мониторинг: своя тонкая прослойка с записью в SQLite (решение Claude, 2026-10-25, по запросу владельца «собирать метрики по временным меткам»)
- **Что хотел владелец:** метрики по временным меткам; пользуется только он; названия источников нужны («вдруг причина ошибки это особый файл»). Поэтому записываются названия источников и тексты ошибок; содержимое источников, вопросы и ответы нет (они не нужны для диагностики, а файл разрастётся).
- **Почему не `tracing`, `metrics`, OpenTelemetry, Prometheus:** нужны локальные длительности по операциям, история с процентилями и список ошибок с именами файлов, читаемые `nb stats` и панелью окна. Эти библиотеки дают сбор и экспорт, а сводку по истории пришлось бы всё равно писать, плюс зависимости и экспортёр, которых некому читать. Пересмотреть, если появится сервер или нужен экспорт в чужую систему.
- **Схема:** одна таблица `metric(at_ms, kind, micros, ok, subject, error, detail, fields JSON)`. Числа в JSON, чтобы новое поле не требовало миграции.
- **Время:** два источника, потому что вопросы разные: настенные часы говорят «когда» (могут прыгнуть), монотонные «сколько длилось». Часы подменяются (`ManualClock`).
- **Чего это не видит (известные пределы):** время отрисовки в окне и задержка самого IPC; память мерится в точках (после старта, после добавления, после загрузки модели) и раз в 30 с, пока открыто окно (`memory.periodic`; у `nb` фонового замера нет, процесс короткий); `command.*` включает ожидание блокировки эмбеддера, чтобы отличить ожидание от работы, смотри `embed.*` внутри; несколько процессов (`nb` и окно) пишут в один файл (WAL, ожидание блокировки 2 с).
- **Находка при проверке:** первая версия не записывала ошибку чтения файла, потому что чтение шло до сервиса. Теперь `source.read` измеряется отдельно, и «особый файл» виден в ошибках с путём и причиной.

## D-16. Модель по подписке ChatGPT: официальный вход, перенесённый из бота владельца (решение Claude, 2026-10-25)
- **Откуда.** Владелец показал, что его FamilyExpenseBot уже подключён через «Sign in with ChatGPT» (виден в настройках ChatGPT в списке приложений со своим лимитом). Код входа был удалён из того проекта коммитом `2625d40`; рабочая версия лежала в `2625d40^` (`internal/adapters/chatgpt`, `internal/adapters/llm/responses*.go`). Перенесено на Rust вместе со схемой тестов (поддельный сервер авторизации, гонка обновлений, отказ, поток событий).
- **Схема (по тому коду и по документации OpenAI для открытых проектов):** OAuth с PKCE, адрес возврата `127.0.0.1:1455/auth/callback`, динамический клиент (приложение называется при первом входе, поэтому появляется отдельной строкой в списке приложений ChatGPT), право `chatgpt.tokens.use.direct`, запросы `POST https://api.openai.com/v1/responses` с `stream=true` и `store=false`, модель берётся из `GET /models` (первая с `visibility=list`) или из выбора владельца: `settings.json` (`nb use`) или `NOTEBOOK_RS_MODEL`. Выбор общий для модели и окна: `ChatGptAccount` держит его в `Arc<Mutex<Settings>>`, `ChatGptLlm` читает на каждом вызове, поэтому смена из окна действует сразу; сохраняется в файл (флаг или переменная в файл не попадают). Владелец выбрал «luna 6» = `gpt-6-luna` с `effort=medium` (в списке аккаунта это единственная luna версии 6; есть ещё `gpt-5.6-luna`).
- **Что проверено вживую (2026-10-25):** вход с реальным браузером и аккаунтом владельца (право на план выдано, токен на час, токен обновления есть, файл 0600); реальный вопрос ушёл через подписку, ответ верный, цитата проверена, вызов в метриках подписан `chatgpt`. Первая попытка входа закончилась по таймауту: подтверждение пришло после пяти минут.
- **Что не проверено:** обновление токена на настоящем сервере (токен прожил меньше часа за время проверки); поведение при исчерпанном плане на настоящем API; условия OpenAI на сегодня (в README бота сказано, что они могут меняться); занятый порт 1455 (тогда берётся свободный, примет ли сервер другой порт, неизвестно).
- **Политика выбора модели.** Вошёл: отвечает ChatGPT. Не вошёл: Codex. Если вход протух насовсем, это ошибка с просьбой войти заново, а не тихое переключение на Codex (скрыло бы, что вход требует внимания).
- **Зависимости (новые):** `sha2`, `base64`, `getrandom` (PKCE и случайные значения; без своей криптографии). `ureq` уже был.
- **Безопасность.** Токены только в файле 0600; не печатаются; не попадают в метрики и ошибки. Выход (`nb logout`, кнопка в «Настройках» с подтверждением «Да, выйти») удаляет файл на этом компьютере; само подключение можно убрать и в настройках ChatGPT.

## D-17. Диалог с историей (2026-10-25, решение Claude по просьбе владельца «обязательно»)
- **Что:** диалог хранится по блокнотам в таблице `message` (роль, вид `ask`/`summarize`/`compare`, текст, JSON с цитатами). Окно показывает его при выборе блокнота; «Очистить диалог» просит подтверждения.
- **Что видит модель:** последние реплики вида `ask` (до 4000 знаков, ответы ассистента обрезаются до 600) в блоке «История диалога (она не источник...)». Факты по-прежнему только из фрагментов, цитаты проверяются как раньше.
- **Поиск для коротких уточнений** (до 60 знаков, «а подробнее?»): запрос = предыдущий вопрос + уточнение. Это эвристика без вызова модели (запрос на переписывание стоил бы ещё секунды). Граница: уточнение длиннее 60 знаков, но без смысла само по себе, найдёт хуже.
- **Конспекты и сравнения** лежат в диалоге для человека, но в историю вопросов не попадают.
- **Не сохраняется:** вопрос, на который модель не ответила (ошибка).

## D-18. Папка как источник и `nb reindex` (2026-10-25, решение Claude по просьбе владельца «обязательно»)
- **Папка:** `add` с путём к папке берёт все `txt`, `md`, `markdown`, `pdf` в ней и во вложенных (глубина до 8, не больше 500 файлов, скрытые и ссылки пропускаются). Название источника: путь внутри папки (`a/notes.md`), чтобы одинаковые имена не затирали друг друга. Плохой файл не останавливает остальные: он попадает в список «не добавлено» с причиной. Окно: кнопка «Папку…» и перетаскивание папки.
- **Не берём из папки:** `html` (локальный HTML сейчас читается как сырой текст, это отдельная доработка) и всё остальное.
- **Текст источника теперь хранится** (`source.text`, миграция до версии 2). Без него нельзя перенарезать: файла или страницы может уже не быть.
- **`nb reindex <блокнот>`:** источники с сохранённым текстом режутся и считаются заново (после смены нарезки или модели поиска); у старых источников (добавлены до версии 2) текста нет, их фрагментам только дописываются векторы текущей модели, а в отчёте они названы, чтобы добавить их ещё раз.
